# F22 — Upload limits: $5 per month hard cap, 3 uploads per browser per day, and a Turnstile bot check

Milestone: M2 · Branch: `feat/F22-upload-limits` · Brief sections: §7 (Limits; Hosting),
§9 (Safe: "Limits are enforced", "No personal data is stored anywhere"), §2

## What the student gets
Nothing to see when all is well: a transcript is read as before. Behind it, PathCheck's
function reads a PDF only for a visitor who passes Cloudflare's bot check, at most three
times a day for one browser, and only while the month's cost at Google is under $5. When
one of these stops an upload the student reads the existing sentence, "Upload isn’t
available right now — try again tomorrow" (its wording and Flow A are F23).

## User-visible change
Small, on the hosted site only: while a chosen PDF is read, Cloudflare's check runs in the
page; it stays out of sight unless Cloudflare wants the visitor to tick a box, which then
appears at the bottom of the window. No new wording of PathCheck's. A development server is unchanged:
no check, nothing sent.

## What is built

### In the function (`netlify/functions/read-transcript.mts`)
After its own refusals (method, type, size, not a PDF, no Gemini key) and before Gemini is
called, in this order:

1. **The bot check.** The browser sends Cloudflare's token in the header
   `x-turnstile-token`. The function asks Cloudflare's `siteverify` (the secret from the
   environment variable `TURNSTILE_SECRET_KEY`, the token, nothing else: no IP address is
   passed on) and goes on only when the answer says success and that the token was made
   for this: the widget is drawn with the action `upload`, and on the published site the
   answer's action must be `upload` and its hostname the site's own (as Netlify names
   it). On a preview, where Cloudflare's test keys answer, those two are not looked at
   (the test keys answer with neither). No token, a failed or expired token, a token
   made for another action or host, Cloudflare not answering in 10 seconds, or no secret set: the upload is
   refused, Gemini is not called, and nothing is counted. One token is good for one
   upload at Cloudflare; Cloudflare itself says two requests sent in the same moment can
   both pass, which the two counters below bound.
2. **Three uploads a day for one browser.** The browser sends a random number of its own
   making in the header `x-pathcheck-browser` (32 hex digits; made new every UTC day, see
   "In the browser"). The function counts uploads under that number for that UTC day. The
   fourth is refused. A request without a well-formed number is refused. Counted is every
   upload that gets past this point, whether Gemini then reads it or not.
3. **$5 a month.** The function keeps the month's cost in millionths of a dollar. The
   month is Google's billing month, the calendar month in Pacific time
   (`America/Los_Angeles`): Google's own cap starts anew on the first of the month
   there, and a month that began hours earlier would allow a second $5 inside one of
   Google's months. (The day of the three uploads stays a UTC day.) Before Gemini is called it adds the most one upload can cost (the
   reservation: the model's whole input window and the most output, at the price list's
   rates); if that would take the month over $5, the upload is refused and nothing is
   added. After Gemini answers, the reservation is replaced by what the upload did cost,
   worked out from the token counts Gemini reports (input, output, and thinking if any)
   at the price list's rates, rounded up. If Gemini refused the request (an HTTP error)
   the reservation is taken off again; if it is not known what was used (no answer in
   time, an answer without counts), if the write that settles the cost fails or keeps
   losing, or if the function is stopped between reserving and settling (Netlify's 60
   seconds, a crash), the reservation stays: the total can run ahead of the real cost,
   never behind it. So the month's real cost cannot pass $5 through PathCheck.
   The prices and the model's limits are constants beside the model's name, dated.
- **Where the counters are kept:** Netlify Blobs (included in the Free plan; the brief's
  first choice), one site-wide store, read with strong consistency and written only with
  Netlify's conditional writes (`onlyIfNew`, `onlyIfMatch`), so that two uploads at once
  cannot both take the last place; a write that keeps losing is tried again a few times
  and then the upload is refused. Previews and the published site share the store: they
  spend from the same balance at Google.
- **What is kept, all of it:** `month/2026-11` → a whole number of millionths of a
  dollar; `day/2026-11-17/<the browser's random number>` → a whole number of uploads. No
  IP address, no cookie, no file name, nothing of a transcript, no time of day. The
  day's entries of earlier days are deleted when a new day's first upload comes.
- **If the store cannot be read or written**, the upload is refused (it fails closed):
  Gemini is never called without both counters having been written.
- **Answers:** a refused check is 403; a limit reached is 429; a store or Cloudflare
  failure is 503 "unavailable". In the browser all of them are the existing sentence
  (F23 owns its wording). The log line stays one fixed line per failure, with new fixed
  words (`check`, `browser`, `day-limit`, `month-cap`, `store`); never a token, a
  browser number or an amount.
- **The function's own note in the log of what an upload cost** is not written: the
  month's total is in the store.

### In the browser (`src/upload.ts`, the built site only)
- Before the PDF is posted, the page gets a token from Cloudflare's widget: its script is
  loaded from `challenges.cloudflare.com` the first time a file is chosen (not when the
  page opens), the widget is drawn in a place of its own beside the page, at the bottom
  of the window (it stays when the page is drawn again or another page is opened:
  changed after the code review, see "Code review"), with
  `appearance: 'interaction-only'` (out of sight unless Cloudflare asks for a tick), and
  the page waits up to 30 seconds for the token while it says "Reading your transcript…".
  When Cloudflare does want a box ticked, the page says so in that sentence's place and
  reads it out: "One more step: tick the box at the bottom of the window." (the agent's
  wording, listed for the owner), and puts the keyboard on the box's place, so that the
  next Tab enters the widget; when the tick is done, or the check ends, it says again
  that it is reading. (Added after QA part 1, round 2: without it a keyboard or
  screen-reader user was not told that a box was waiting.)
  No token (the script blocked, the check failed, the wait ran out): the existing
  sentence, and nothing is posted.
- The site key is public by design. It comes into the build from the variable
  `VITE_TURNSTILE_SITE_KEY`.
- The browser's random number: 16 random bytes from the browser's own generator, kept in
  the browser under `pathcheck.browser` together with the UTC day it was made for, and
  made new when the day is another. It says nothing about the person or the device and
  links nothing from one day to the next. It is the third thing PathCheck keeps in the
  browser (F19's list `STORED_KEYS` and its tests "keeps only what the result needs" and
  "clears everything" are extended, and its records). "Clear my data" removes it like
  everything else PathCheck keeps (a student who clears their data gets a new number: the day's
  limit is a brake on ordinary use, not a wall; the bot check and the month's cap are
  the walls).
- The request to the function now carries the PDF, the content type and those two
  headers; nothing else.

### Keys and deploys
- **Published site (Netlify's Production context):** the owner's real Turnstile keys, made
  for the hostname `pathcheck.netlify.app`: `VITE_TURNSTILE_SITE_KEY` (not a secret: it is
  in the page) and `TURNSTILE_SECRET_KEY` (a secret). The owner also adds
  `GEMINI_API_KEY` for Production once this feature is merged (F21's record).
- **Deploy Previews:** Cloudflare's widget only works on the hostnames it is made for, and
  a preview has its own hostname for every pull request. So on a preview, where the two
  variables are not set, the page and the function use Cloudflare's published test keys
  (always pass). They are used only when Netlify says the deploy is a Deploy Preview;
  on the published site a missing key means every upload is refused. A preview is
  therefore protected by being Private and by the month's cap, not by the bot check.
  The day's count does not hold back a script there, which can send a new browser number
  with every request. Listed for the owner.
- **A development server:** as before, no function, no check, nothing sent. (A built copy
  served on one's own machine, `npm run preview`, behaves as the hosted site does.)
- **The hostname the bot check must name** on the published site is the site's main
  address as Netlify gives it. F24's staging address is that address (Netlify's
  Production context), not a branch deploy.

### Other
- `@netlify/blobs` becomes the project's first dependency that runs on the server. The
  function's tests that said "the function imports nothing and stores nothing" now say:
  it imports that one package, and stores the two kinds of numbers above and nothing
  else.
- The build check also fails when the built site holds `TURNSTILE_SECRET_KEY` or
  Cloudflare's `siteverify` address.
- The reader check (`scripts/reader-check.mjs`) sends Cloudflare's test token and a
  random browser number, so that it still runs against a preview: six runs need two
  browser numbers.

## Acceptance checks
Tests: `tests/read-transcript.test.ts` (`function`: the function with stand-ins for
Gemini, Cloudflare, the store and the clock), `tests/upload.test.ts` (`upload`: the browser
side with a stand-in widget), `tests/limits.test.ts` (`limits`: the counters and the cost
on their own), the build check's test. "Hosted": on a Deploy Preview, run by the owner or
judged from the owner's screenshots, as for F21 (the project is Private and the agent
sends no file to an outside address).

1. **The bot check is asked, on the server (step 3).** With a token: one request to
   Cloudflare's `siteverify` with the secret and the token and no IP address; success
   with the action `upload` and the site's own hostname → the upload goes on. On the
   published site a token made for another action or another hostname is refused. Without a token, with success false (each of Cloudflare's error
   codes), with Cloudflare answering an error, not answering in 10 seconds or not being
   reachable, or with no secret on the published site: refused, Gemini not called,
   neither counter changed. — `function` "refuses an upload that fails the bot check".
2. **Three a day for one browser (step 2).** The same browser number: uploads 1, 2 and 3
   are read, the fourth is refused with 429 and Gemini is not called; another browser
   number the same day is read; the same number the next UTC day is read again; a
   missing or malformed number is refused. An upload that Gemini fails still counts. —
   `function` "reads three uploads a day for one browser"; `limits`.
3. **$5 a month, hard (step 1).** With the month's total at $5 minus less than one
   reservation: refused with 429, Gemini not called, the total unchanged. Below that:
   read, and afterwards the total has grown by exactly the upload's cost from Gemini's
   counts (worked examples with the price list's rates, thinking counted as output). A
   new month, as Google bills it, starts at zero: an upload at 2026-12-01 02:00 UTC is
   still in November (Pacific time) and counts there; one at 2026-12-01 09:00 UTC is in
   December. Gemini answers an HTTP error: the reservation is taken off. Gemini does not
   answer in time, or answers without counts; the settling write fails or keeps losing;
   the function is stopped after reserving: the reservation stays. For any sequence of
   uploads, generated, with those failures among them: the total is never under the sum
   of the real costs and never over $5. — `function` "stops reading when the month reaches $5";
   `limits` "holds for any uploads".
4. **Two at once cannot both take the last place.** With a stand-in store that behaves as
   Netlify's does (conditional writes): two uploads started together at count 2 → one is
   read, one refused; two started together one reservation under the cap → one is read,
   one refused; a store that never lets the write win → refused after a few tries,
   Gemini not called. — `limits` "lets one of two take the last place".
5. **It fails closed.** The store cannot be read, or cannot be written: 503, Gemini not
   called. — `function` "reads nothing when the counters cannot be kept".
6. **No personal data (step 4).** After a run of uploads, everything in the stand-in
   store: only keys of the two forms and whole numbers as values. The function's source
   reads of a request only its content type, its length and the two headers; it names no
   IP address, cookie or user agent; nothing it logs holds a token, a browser number or
   an amount. Old days' entries are gone after a new day's first upload. — `function`
   "keeps two kinds of numbers and nothing else", "logs nothing of the limits".
7. **The browser side.** On the built site: the widget's script is asked for only when a
   file is chosen, from `challenges.cloudflare.com`; the token and the browser's number
   go in their two headers; the number is 32 hex digits, the same for a second upload the
   same day, another the next day, gone after "Clear my data" (F19's tests of what the
   browser keeps, extended: `tests/remember.test.ts`); no token in 30 seconds or
   a blocked script → the existing sentence and nothing posted; when the widget asks for a
   tick, "One more step: tick the box at the bottom of the window." stands where the
   reading sentence stood and is read out, the keyboard is on the widget's place, which
   is one element beside the page that a redraw or a page change does not remove, and
   after the tick the reading sentence is back (`tests/turnstile.test.ts` "tells the
   page when a box waits to be ticked"; `tests/left-page.test.ts` "says when the bot
   check wants a box ticked"); 403 and 429 → the
   existing sentence. On a development server none of it happens. — `upload`.
8. **Keys by deploy.** The function uses Cloudflare's test secret only when Netlify says
   the deploy is a Deploy Preview and no secret is set; on the published site without a
   secret every upload is refused. The page built without a site key uses the test site
   key. The real secret is in no file of the repository and not in the built site. —
   `function` "uses the test keys on a Deploy Preview only"; `build`.
9. **Every limit has its test (step 5).** Checks 1 to 5 name them; each is shown to fail
   when its limit is taken out (the evaluator's mutations).
10. **Hosted, on a Deploy Preview** (the owner's key for Gemini is there already): a
    made-up PDF is read as before (the reader check passes: both PDFs, three runs each,
    with two browser numbers); a fourth upload with one browser number the same day gets
    the existing sentence; the Network list of a successful upload shows the widget's
    requests to `challenges.cloudflare.com`, one request to `/api/read-transcript` and
    none to Google; no console error of the page. — hosted.
11. **Hosted, on the published site, with the owner's real Turnstile keys:** this needs
    the owner to publish and to set the three keys for Production; it is looked at with
    F24 (the staging address), and listed there. F22 passes on checks 1 to 10.
12. **Records.** Decision log: what counts as an upload, the UTC day and month, the
    reservation and its figure, the browser's number and why it is not personal data,
    the test keys on previews, Netlify Blobs and what the Free plan says of its cost;
    `docs/CURRICULUM-HANDOVER.md` is not touched.
13. `npm run check` passes.

## Waiting for the owner
- **For the owner to know:** a Deploy Preview has no real bot check (Cloudflare's test
  keys always pass there). It is reachable only by the owner while the project is
  Private. Whenever the owner opens the project to the public, anyone with a preview's
  address can upload; a script can get round the day's count (a new browser number each
  time), so only the month's cap stops it there. Because previews and the published site
  count the same month, such abuse would use up the month for the published site too:
  uploads everywhere would say "not available" until Google's next month. Open the
  project only for the minutes of a test.
- **For the owner to know:** PathCheck's count of the month starts at zero when this is
  first used, while Google already counts what was spent before (about $0.04 in November
  2026). The reservation's margin (36 cents) is larger than that.
- **Turnstile keys** (brief §12): a widget for `pathcheck.netlify.app`, its site key and
  its secret, set in Netlify for Production. Needed for check 11 (F24), not for building
  or for checks 1 to 10. The exact clicks are given once this contract is agreed.
- **A note for the owner, not a question that blocks:** Cloudflare's check loads a script
  from Cloudflare when a file is chosen; Cloudflare then sees the visitor's browser and
  address, as any bot check does. The privacy sentence speaks of Google only. The brief
  asks for the check; whether the sentence should name it is the owner's choice.
