# F21 — The only server piece: one function sends the PDF to paid Google Gemini and returns the course rows

Milestone: M2 · Branch: `feat/F21-read-transcript` · Brief sections: §7, §9 (Safe; "The
transcript reader passes on synthetic transcripts"), §2

## What the student gets
On the hosted site, a student can choose their own unofficial transcript PDF and see the
rows that were read from it in the review step, where every row has been checked by
PathCheck's own code before it can count. On localhost nothing changes: the two made-up
transcripts are still answered from their prepared rows, and nothing is sent anywhere.

## User-visible change
Yes, on the hosted site only: a chosen PDF is read (until now every file was answered
"Upload isn’t available right now — try again tomorrow" there). No new screen, no new
wording. The limits and the bot check are F22, the outage wording is F23, the staging
address and the owner's own upload are F24.

## What is built
- **One Netlify Function**, `netlify/functions/read-transcript.mts`, served at
  `POST /api/read-transcript`. The request body is the PDF's bytes and nothing else (no
  file name, no cookie, no identifier).
  - It refuses, before anything is sent on: another method (405); a body that is not
    `application/pdf` (415); more than 4 MB (413: Netlify's own limit for a binary body is
    about 4.5 MB); bytes that do not start as a PDF (415).
  - It sends the PDF once to Google Gemini's `generateContent` endpoint, inline, with the
    key in the `x-goog-api-key` header (never in the address), a fixed instruction and a
    fixed answer shape (a list of rows: term, transfer, prefix, number, description,
    attempted, earned, grade, points). One model, named in one constant; no retry;
    temperature 0, so that the same PDF is read the same way; a fixed most for the length
    of the answer, so that one upload has a known highest cost.
  - It waits 25 seconds for Gemini and no longer (Netlify stops a function at 60): after
    that it answers "unavailable" itself, so the student gets the plain sentence and not
    a platform's error page.
  - It answers `{ "rows": [...] }` with, for each row, only those nine named fields, each
    a short piece of text, a number, true/false or nothing. Anything else in Gemini's
    answer is dropped. It does not judge the rows: that is F10's code, in the browser.
  - Anything that goes wrong (no key set, Gemini refuses or is down or too slow, an answer
    that is not a list of rows) is one answer: 503 `{ "error": "unavailable" }`.
  - Every answer carries `Cache-Control: no-store`. Nothing is written anywhere: no file,
    no Blob, no cache. The log gets one fixed line per failure (what kind, and Gemini's
    status number), never a byte of the PDF, a row, a file name or Gemini's words.
- **The key** is read from the environment variable `GEMINI_API_KEY`, which the owner sets
  in Netlify. It is in no file of the repository and in no answer of the function.
- **Who can reach the key before the limits exist.** Until F22 is merged the owner sets
  the key for the **Deploy Previews** context only. The site's main address (published
  from `main`) and branch deploys then have no key: the function answers "unavailable"
  there and sends nothing to Google. A Deploy Preview's address is public while the key
  is set, and until F22 the owner's prepaid balance and spend cap at Google ($5) are the
  only stop: listed for the owner. The owner adds the key for Production after F22.
- **The browser side** (`src/upload.ts`): on a development server, as today (the made-up
  transcripts only, nothing sent). On the built site, a PDF that passes the checks in the
  browser (a PDF, not over 4 MB) is posted to `/api/read-transcript`, and the answer goes
  to `openTranscript`, that is through `readRows` (F10), exactly like a prepared answer.
  Any failure is the existing refusal "Upload isn’t available right now — try again
  tomorrow"; 413 and 415 are the existing "too large" and "not a PDF" sentences.
- **`netlify.toml`**: the build command, the published folder and the functions folder, so
  that the owner types no build setting.
- **The reader check**, `scripts/reader-check.mjs <address>`: posts each made-up PDF to
  the function at that address, puts the answer through `readRows`, and compares it with
  the rows prepared for that PDF (`synthetic/transcripts/<name>.json`): the same rows in
  the same order, none to fix, the totals lines not among them. The fields that decide
  anything compare exactly (term, transfer mark, course code, credits, earned credits,
  grade, points): one difference fails the check. The description, which is only shown,
  compares after collapsing spaces and ignoring capitals; any difference left is printed
  and recorded, and fails the check. It prints the model version Gemini reports and only
  the made-up data. It is run by the agent against a Netlify Deploy
  Preview of this pull request once the owner has set the key; it is not part of CI,
  which has no key and must not spend money.
- **The build check** (`scripts/check-build.mjs`) also fails when the built site holds the
  name of the key's variable, Gemini's address or the key header: the server piece and
  its key never ship to the browser.

## Acceptance checks
Tests: `tests/read-transcript.test.ts` (`function`: the function called directly with a
stand-in for Gemini and for the log), `tests/upload.test.ts` (`upload`: the browser side),
`tests/build-check.test.ts` or the existing test of `check-build.mjs` (`build`). "Reader
check": `scripts/reader-check.mjs` against the Deploy Preview, with the real Gemini.
"Evaluator": a real browser on the Deploy Preview, made-up transcripts only.

1. **One function, one call (step 1).** A posted made-up PDF is sent to Gemini exactly
   once: to the `generateContent` address of the one model, with the PDF inline, the
   instruction and the answer shape; the function answers 200 with the rows of Gemini's
   answer. — `function` "sends the PDF to Gemini once and returns its rows".
2. **The key stays on the server (step 2).** The key is sent to Gemini in the header only
   and is in no address; no answer of the function, in success or failure, holds it, even
   when Gemini's own error text repeats it; the repository has no key (the function reads
   `GEMINI_API_KEY` from the environment and nothing else); the built site holds neither
   the variable's name nor Gemini's address; the browser's request to the function carries
   no key and no header of its own besides the content type. — `function` "keeps the key
   out of every answer"; `upload` "posts the PDF and nothing else"; `build` "the built
   site holds nothing of the server piece".
3. **Never stored, never logged (step 3).** The function's source imports no file system,
   no Blobs and no cache, and calls nothing but Gemini. With the log captured, for a
   success and for every failure: no byte of the PDF, no row, no description, no grade, no
   file name and none of Gemini's text is logged; a failure logs one fixed line. Answers
   carry `Cache-Control: no-store`. The browser keeps of the file what F19 already keeps
   (the reviewed result), not the PDF. — `function` "logs nothing of the transcript",
   "stores nothing"; evaluator (the function log in Netlify cannot be read by the agent's
   tools unless the owner looks: listed for the owner).
4. **The answer is untrusted (step 4).** What the function returns goes through
   `readRows`: a row with a bad code, bad credits or an unknown grade is a row to fix and
   counts nothing; a totals line is thrown away; a field that is not one of the nine is
   not passed on; text is cut to a short length; an answer that is not a list of rows, or
   is not JSON, or is cut off, is "unavailable" and nothing is taken on; an instruction
   printed inside a PDF cannot make a row count, because no row counts without passing
   F10's checks. — `function` "passes on only the named fields", "answers unavailable for
   an answer that is no list of rows"; `upload` "puts the answer through the same checks
   as a prepared one".
5. **Refusals before anything is sent.** Not POST; not `application/pdf`; over 4 MB (by
   the declared length and by the bytes themselves); not a PDF: Gemini is not called, and
   the answer is 405, 415, 413, 415. No key set: 503 "unavailable", Gemini not called. —
   `function` "refuses before calling Gemini".
6. **Failures are one answer.** Gemini answers 400, 401, 403, 429 or 500; does not answer
   within 25 seconds (a stand-in that never answers); answers with no text; answers
   blocked or cut off at the most length: 503 `{ "error": "unavailable" }`, the same for
   each, and in the browser "Upload isn’t available right now — try again
   tomorrow" with nothing taken on. — `function` "answers unavailable when Gemini fails";
   `upload` "says upload isn’t available".
7. **The browser side.** On the built site a chosen PDF is posted as it is; the review
   step then shows the rows as for a prepared answer; a file that is not a PDF or is over
   4 MB is refused in the browser and nothing is sent; on a development server nothing is
   ever sent, and the made-up transcripts work as before. — `upload`; the existing
   `flows`, `left-page` and `check-page` tests unchanged.
8. **The reader passes on the made-up transcripts (step 5).** For `sample-a.pdf` and
   `sample-b.pdf`, the function on the Deploy Preview, with the real Gemini, returns rows
   that `readRows` takes on as exactly the prepared rows: same count and order, and per
   row the same term, transfer mark, code, description, credits, earned, grade and
   points (the description after collapsing spaces and ignoring capitals); no row to fix;
   and both flows then show what they show on localhost (`sample-a`: 81 credits left).
   Run three times each: the same every time. — reader check (recorded in "QA rounds"
   with the date, the model version Gemini reports and the three results);
   `function` "returns the expected rows for each made-up PDF" proves the same path with
   the stand-in. **This check waits for the owner:** it needs the Netlify project and the
   key (see "Waiting for the owner").
12. **No key, no call.** On a deploy without the key (the site's main address until the
    owner adds the key for Production after F22): choosing a PDF gives "Upload isn’t
    available right now — try again tomorrow", nothing is taken on, and nothing is sent
    to Google. — `function` "refuses before calling Gemini" (no key set: Gemini's
    stand-in is never called); evaluator, on the main address once it is published.
9. **On the hosted page**, with a made-up PDF chosen on the Deploy Preview: the review
   step, "Continue", both flows, no console error; the browser's network log shows one
   request to `/api/read-transcript` and none to Google. — evaluator. Waits for the owner
   like check 8.
10. **Records.** Decision log: the function's address and limits, the model and why, the
    variable's name and its context until F22, what is logged, the Netlify project as the
    staging site. The sentence about the PDF on both pages that show it ("Check my
    courses", "See what I have left") is the one the owner has approved for M2: if the
    owner changes it, the new sentence goes in with its tests and DESIGN.md.
    `features.json`: F21 `passes`, `evidence`, `tests` only after checks 8 and 9 and after
    the owner's answer about that sentence.
11. `npm run check` passes.

## Waiting for the owner
- **The Netlify project and the key** (asked on 2026-11-16, with the steps): without them
  checks 8 and 9 cannot run. Everything else is built and tested first.
- **A question that blocks F21's `passes`, not the build: the privacy sentence.** From M2 the PDF is sent to
  PathCheck's function, which keeps nothing, and from there to Google Gemini's paid
  service. Google's terms for paid services say it does not use the content to improve
  its products, and that it logs prompts "for a limited period of time, solely for
  detecting and preventing violations". So "read, then deleted" is exact for PathCheck
  but not, for that limited period, for Google; and the sentence does not say that the
  PDF goes to Google (brief §7: "one plain sentence says what is sent and that it isn't
  kept"). The sentence is the owner's; a proposal is put to the owner in chat and in the
  pull request.
- **No pull request before the owner's setup** (the owner, 2026-11-16, in chat: "do not
  create pull request until I setup the system from the 3 steps you provided."). F21 is
  built and tested on its branch meanwhile.
