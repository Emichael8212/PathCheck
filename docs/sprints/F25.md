# F25 — Curriculum handover: how to review and update the curriculum each year

Milestone: M3 · Branch: `feat/F25-curriculum-handover` · Brief sections: §5 (the academic
rules and their table), §4 "On every result" ("Curriculum last reviewed: <date>"), §9
(Live: "`docs/CURRICULUM-HANDOVER.md` explains how to review and update the curriculum
each year"), §12

## What the student gets
Nothing changes on the pages. The student gets a PathCheck whose curriculum can be kept
true after its builder is gone: once a year the person responsible for PathCheck checks
the curriculum against the department's and sets the date the pages show.

## User-visible change
No page changes. Visual design is not graded (a guide in Markdown has no design to match).
Clarity is graded on the guide itself, read as its reader would: a person who is not a
developer.

## Why tests change too
Today the guide could not be followed to a green check. Tried in a scratch copy (contract
review, round 1): a new review date in the curriculum file and in the one test that
quotes the owner fails ten tests in five other files, which repeat the date or its
month; a course added to a pick fails tests that repeat the curriculum's lists and
counts. So this feature first makes the curriculum's own content written in as few
places as it can be, and only then writes the guide. No page and no rule changes.

## What is built

### 1. The tests stop repeating the curriculum (no app code changes)
- **The review date.** Every test that states the real review date or its month and year
  takes it from the curriculum file (`tests/start.test.ts`, `tests/flows.test.ts`,
  `tests/print.test.ts`, `tests/remember.test.ts`, `tests/trust.test.ts`, and any other
  the build finds). The tests of the sentence about an old review work out their "today"
  from the file's date (the first day the sentence shows, and the day before). **One
  statement of the date stays on purpose:** `tests/curriculum.test.ts` "carries the
  last-reviewed date", which quotes the owner's review. So the date is written in two
  places: the curriculum file and that test.
- **The table.** `tests/curriculum.test.ts` "matches the table in brief section 5" reads
  the table from `docs/BRIEF.md` itself in place of its own copy, and the number of
  courses ("lists each course once") is counted from that table. The brief stays the
  statement of the curriculum; the data file must equal it. So a course is written in
  two places: the curriculum file and the brief's table.
- **Lists and counts repeated in passing.** A test that repeats the real curriculum's
  lists or counts while proving something else takes them from the curriculum file,
  where that keeps what the test proves. Each such change is listed in this file with
  what the test still proves. Found so far:
  - `tests/placement.test.ts` "reaches 121 with everything passed" and
    `tests/plan.test.ts` "holds for any transcript and settings": the counts of pick
    courses and the like.
  - `tests/checklist.test.ts` "matches the approved design's student": the approved
    design's numbers (27 counted, 13 in progress, 81 left, 121) and its passed and
    in-progress courses **stay stated**. Only the text of an open pick's alternatives is
    taken from the curriculum file.
  - `tests/mockups.test.js` "uses real titles for every course it names" **stays as it
    is**: the M0 mockups are a frozen record of the approved design and are compared
    with the curriculum file. So a new title for a course that the mockups name is a
    hand-over. No test is left reading both of its sides from the same file.
- **A test that proves a rule with particular courses stays as it is**
  (for example the answers for MGT 321, PSY 251 or GEO 206): the curriculum is part of
  what those tests state, and a change to one of those courses is a hand-over (below).
- Proof that nothing was weakened: for each changed test, a mutation of the app code that
  the test caught before is still caught (recorded here; the evaluator repeats some).

### 2. `docs/CURRICULUM-HANDOVER.md`
For a reader who is not a developer and has never seen the code: the person responsible
for PathCheck, whoever that is by then. It can be followed with a GitHub login and a
browser; nothing has to be installed. The yearly routine fits on one screen at the top;
the details are below it. It says:
- **When and why.** Once a year, and whenever the department changes the curriculum. The
  pages say "Curriculum last reviewed: <month year>"; twelve months after the review date
  every page shows a sentence that the review is old, until the date is set again. The
  rule, and one worked example labelled with its own date ("a review dated 2026-11-15
  shows the sentence from 2027-11-16"): the guide does not state today's value, so it
  does not need editing every year.
- **Who decides.** What the curriculum requires is decided by the university and
  confirmed by the person responsible for PathCheck. Nobody guesses a rule. A change is
  written down in `docs/decision-log.md` before the brief's table and the data change.
- **What to compare.** The department's current curriculum guide for the B.S. CIS against
  the table of the brief's §5, block by block, then the rules under it. As a step of the
  routine: `sources` in the curriculum file says what was compared, and when.
- **Outcome 1: nothing changed.** Set the review date in its two places, step by step in
  the browser: edit the file, "Commit changes...", a new branch (never directly to
  `main`), a pull request, the second file on the same branch, a green check, merge.
- **Outcome 2: something changed.** Only the kinds of change that the evaluator has
  followed to a green check with no edit outside the places the guide names (check 5)
  are called doable. Expected: a course replaced in a pick, added to a pick or taken out
  of one, and a title. The guide says that for some courses such a change will still be
  a hand-over (a course that PathCheck's own tests use as their example), and that the
  "Is this mine?" rule is how the reader finds out. For each: the curriculum file, the brief's table (a title is not
  in it), `sources`, the decision log, the review date. A kind that cannot pass that way
  is listed under the hand-over instead.
- **"Is this mine?"**, as a rule the reader can apply without knowing the code. The pull
  request's check is green: done. It is red: open "Details" and look in this order.
  - A line that names `docs/curriculum/provisional-current.json` with a line and a
    column (as in `error TS1005: ',' expected.`): the file is broken at that place (a
    missing comma or quote). Fix it there. (The check stops before any test runs, so no
    line says "FAIL".)
  - Lines containing "FAIL": if the test is one of those the guide names with what each
    means (the table test: the file and the brief disagree; the loader's refusals; the
    date test), fix what it says; if it is any other test, hand it over.
  - Neither: hand it over.
  And whatever the check says: a change to how a rule works (grades, electives, the
  sequence, legacy courses, credits, the degree's total) is handed over.
- **The hand-over:** what to write down, and a request that can be given as it is to a
  developer or to Claude Code; nothing is merged while the check is red.
- **The curriculum file, field by field**, in plain words with one example each.
- **Mistakes PathCheck catches**, each with the words the red check shows: a missing
  comma or quote (the likeliest in a browser), a block whose credits do not add up, a
  course listed twice, a date that is not a date, the file and the brief's table
  disagreeing.
- **Who merges, and publishing.** Merge only on a green check. Then Netlify's Deploys
  page: if it says "Auto Publishing Locked", publish the newest "Production: main@…"
  deploy by hand (the clicks of M2); if not, the merge published it. Then what to look
  at on the site: the footer's "Curriculum last reviewed: …", the top line of the
  printed summary, and no sentence about an old review. Nobody is told to deploy from a
  command line.

### 3. `tests/handover.test.ts`, which keeps the guide true
- Every file and command the guide names exists. A quoted line of a file is written in
  the guide as a fenced block headed by the file's path, and is in that file word for
  word.
- Every field of the real curriculum file, at every level, is explained in the guide (the
  list is taken from the file, so a new field without an explanation fails).
- The guide's worked example of the date is true by `reviewIsOld`.
- The changes the guide walks through, made to a copy of the curriculum in memory with a
  fixed "today" (the review date; a course replaced in a pick, added and taken out; a
  title), are taken by the loader, and the pages then say the new month and year and no
  sentence about an old review.
- Each mistake the guide lists is refused, with the words the guide quotes (for the
  broken file: it does not parse).
- The guide does not say "ask your advisor" and names no person or office to ask.

### 4. Records
A link to the guide from `README.md`; the decision-log rows; the carried-forward line
about the banner removed; and, in the M3 milestone file when it is written, an owner step:
the owner follows the guide's clicks on GitHub once (the agent cannot: it has no GitHub
login in a browser, and a rehearsal pull request would be a real one).

Nothing else. No screen, no script, no second curriculum, no editor.

## Decided here (recorded in `docs/decision-log.md`; none is an academic rule)
- The guide's main path is GitHub in the browser; a request for a developer or Claude
  Code is the hand-over, not the only way.
- The review date is written in two places and a course in two; tests that repeated them
  take them from those places. No script is added.
- The guide names the department's curriculum guide as what to compare with, and no
  person or office to ask.

## Acceptance checks
1. **The guide exists and a non-developer can follow it** (features.json step 1): every
   step says where to click or what to type; every word a non-developer may not know is
   explained once or not used; the routine fits on one screen at the top. — evaluator.
2. **The review date** (step 1): where it is shown, the rule for the sentence about an old
   review with the labelled example, and how to set it in its two places. —
   `tests/handover.test.ts` "names what exists", "gives a true example of the date";
   evaluator.
3. **The date alone works** (step 2). In a scratch copy the evaluator changes exactly the
   two places to a later day, with no other edit: `npm run check` passes and the built
   page says the new month and year. — evaluator; `tests/handover.test.ts` "takes the
   changes the guide walks through".
4. **How to update the curriculum data** (step 1): each doable kind with what to edit; the
   "Is this mine?" rule; the hand-over with its request; every field explained;
   `sources` as a step. — `tests/handover.test.ts` "explains every field of the
   curriculum file"; evaluator.
5. **Following it works** (step 2). For **every** kind of change the guide calls doable,
   the evaluator, in a scratch copy and doing only what the guide says, makes that change
   to a course of the evaluator's own choosing (not named here or in the guide) and the
   review date: `npm run check` passes with no edit outside the places the guide names.
   If the change is red only on a test the guide does not name (the chosen course is the
   example of a rule test), that is the hand-over working: the evaluator records it and
   chooses another course. **A kind is doable when it passes for a course that no rule
   test uses; it is moved to the hand-over when it fails for such a course.** The
   evaluator also tries one required course replaced: the guide calls that doable only
   if it passes in the same way. — evaluator; `tests/handover.test.ts`.
6. **A change that is not the reader's is sent to the hand-over.** The evaluator makes one
   change outside the doable kinds (for example a course that the answers' tests use):
   the check is red on a test the guide does not name, and the guide's rule and wording
   lead to the hand-over. — evaluator.
7. **A mistake is caught** (step 2's other side). Each mistake the guide lists makes the
   check fail with the words the guide quotes. For the broken file those words are the
   line `npm run check` prints (`docs/curriculum/provisional-current.json(<line>,<column>):
   error TS1005: ',' expected.` for a missing comma), taken from a real run and not
   from a test: in memory the test can only prove that such a text does not parse. —
   `tests/handover.test.ts` "refuses the mistakes the guide names"; evaluator (two of
   them by hand in a scratch copy with `npm run check`, the broken file one of the two).
8. **It invents no rule and sends nobody to an advisor.** — `tests/handover.test.ts`
   "sends nobody to an advisor"; evaluator.
9. **Merging and publishing.** Merge only on green; the guide tells the locked case from
   the unlocked one and gives the clicks and what to look at afterwards; no command-line
   deploy. — evaluator.
10. **The guide stays true.** A file, command, quoted line or field that no longer exists
    or is no longer explained fails `tests/handover.test.ts`. — the evaluator breaks one
    of each in a copy.
11. **The tests still prove what they proved.** For each test changed under "1.", the
    recorded mutation is still caught; no rule test with particular courses was changed;
    no app code changed (`git diff` touches no file under `src/` or `netlify/`). —
    evaluator.
12. **Records** as above; `features.json` F25 `passes`, `evidence`, `tests`.
13. `npm run check` passes.

## Out of scope
- The contact email and the public site (F26).
- Changing the review date now: by the owner's word of 2026-11-17 it stays 2026-11-15.
- A second curriculum, catalog years, or an editor for the curriculum.
- Changing any academic rule or any page.
- Making a change to a course that the rule tests use as an example doable without a
  developer.
